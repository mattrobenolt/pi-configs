# Model Guide

A living evaluation doc for picking which model a subagent should run on — and a light policy layer that shapes agent model selection over time. It accumulates findings rather than getting rewritten each pass.

Specs are from `pi --list-models` (operational truth for this setup, not vendor headlines). Prices are USD per 1M tokens, list price; the Fireworks-hosted rows reflect the configured `fireworks` provider. **AA Index** is the Artificial Analysis Intelligence Index (independent composite, ~0-100) — the one neutral number available across all ten. Context-window caps are intentional, not deficiencies (see the note at the bottom).

## How to maintain this doc

- **Findings logs are append-only.** Each model has a dated `Findings log` that accumulates evidence. Never edit a past finding in place — append a new dated entry that supersedes it if the picture changes, and update the stable blocks above to reflect the current synthesis.
- **Stable blocks evolve.** `What it is`, `Vendor claims & methodology`, `Neutral evals`, `Behavioral properties`, `Pros`, `Cons`, `When to use`, `When not to use` are the current synthesis — rewrite them as understanding improves. The Findings log is the audit trail.
- **Skepticism is the default.** Vendor claims go in `Vendor claims & methodology` with the methodology critiqued. `Neutral evals` is the field that matters most — hunt for the independent number that confirms, qualifies, or contradicts the vendor headline. Every model in this guide had a vendor headline that partially failed a neutral cross-check; assume the same of future models.
- **Source briefs live in `research/<slug>.md`** (next to this file in the skill dir). Log a top-level Changelog entry when a model's synthesis materially changes.

## Selection protocol

**Default to DeepSeek V4 Flash 0731 at `max` thinking** (`fireworks/accounts/fireworks/models/deepseek-v4-flash-0731`). GLM-5.2-class capability at a fraction of the cost, proven in local pi-harness duels (12/12 vs GLM on Matt-shaped coding tasks at both `high` and top gear; ~4x cheaper per accepted task at `high`, ~12x at `max`-vs-`xhigh`; needle retrieval + exact-wording probes clean to ~925K tokens). Run it at `max`: same cost as `high`, faster, vendor's recommended agent config. Text-only. Two hard bans: never a verifier (84% hallucination — generates rather than refuses), never thinking-on + strict `json_schema` (schema-valid integer corruption). GLM 5.2 keeps the long-horizon marathon seat — DeepSeek's known risk is error compounding in ungated long loops, untested locally. See its section + `research/deepseek-v4-flash-0731.md`.

**Carve-out: Drew's review pipeline stays on GLM 5.2 (Matt, 2026-08-12).** The 12/12 duel measured coding tasks, not review — review-quality parity is unmeasured, and DeepSeek's generates-rather-than-refuses failure mode is worst-case for review output (claims a human acts on). Drew's main session also stays GLM: the personality prompt is tuned against it and a model swap without evals is a voice change. DeepSeek's seats in the drew repo are the mechanical ones (test-review lens, worker planning fallback).

**GLM 5.2: long-horizon marathons + former default.** Rescoped 2026-08-07 after the DeepSeek duel. Still the pick for multi-day project-context work where its track record holds, and the fallback if DeepSeek's provider or behavior degrades. Same caveat as ever: silent under-counting — don't use it as a verifier where unflagged wrong numbers are costly.

**Open-weight bias for day-to-day; closed when it makes sense.** Day-to-day work leans GLM / Kimi / MiniMax. Pull closed models (Claude, GPT) in for quorums or when their specific strength is the point. Don't default to them just because they're frontier — and don't trust "closed beats open" headlines: under neutral harnesses the closed-model coding leads shrink or reverse (see Opus 4.8, GPT-5.5).

**Kimi K3 is additive: paired frontier executor + hard-task escalation.** It does not replace GLM 5.2, Opus 5, Sol, or Fable. Use it for difficult repo-scale coding and vision when its frontier-cluster DeepSWE result justifies the premium. Preferred hard-work pattern: **Opus 5 plans/reviews → K3 implements → mechanical checks or the parent accept**. This is a routing recommendation, not a measured K3+Opus collaboration result; the published pairing evidence is Fireworks's K3+Fable oracle-routing study. Never let K3 define and accept its own success criteria — its explicit imaginary-grader/eval-maxxing failure mode makes that unsafe. Post-launch operational reality: throughput is provider-split — Fireworks serves K3 at ~163 tok/s with ~1s first-chunk (interactive-viable; Matt runs it interactively), while the first-party Kimi API crawled at ~33 tok/s under launch congestion. Write its tasks with explicit non-goals (it acts on ambiguity) and bound its runs with turn/token budgets; reasoning effort is the latency lever (thinking can't be disabled, but `low`/`high` cuts the long think).

**Qwen3.8-Max is additive: the Alibaba quorum seat + a GDPval-class knowledge-work niche.** Its headline coding position — DeepSWE v1.1 57% ±3 at $3.73/task, between GLM 5.2 (44 ±2) and K3 (69 ±5) — looks like a mid-tier escalation seat but mostly isn't one: cost per successful task (task cost ÷ pass@1, crude independent-retry math) lands at **$6.54 for Qwen vs $6.74 for K3** — parity — and K3 wins in one shot more often, with vision, on our route. The durable values are structural and specific: a seventh independent family for quorums, and the one neutral row where it leads something — GDPval-AA 1739 Elo, ahead of K3 (1685), behind only Opus 5 (1852) — earned by grinding (64 steps/task vs a 14-step median), and unverified locally. Never a verifier: AA-Omniscience hallucination regressed 23%→40%. Optionality watch: if the Fireworks route upgrades to 1M/vision, $2/$6 starts pressing K3's seat. See its section + `research/qwen3p8-max.md`.

**Quorums across discrete families for decisions.** For review, critique, or design choices, run models from *different* families — not several from one vendor. Families: Anthropic, OpenAI, Moonshot, MiniMax, Z.ai, DeepSeek, Alibaba (Qwen). Fireworks is a host, not a family. A valid 3-family quorum is `Opus 5 + GPT-5.6-sol + Kimi K3`; `Opus + Sonnet + Fable` is not (all Anthropic). Quorums are for decisions, not every execution task.

**Fable 5 is a consciously-invoked juggernaut.** Very good, very expensive, and latency-bound (109s to first token at max effort — batch/async only). Pull it in only when the work is deemed worth it. Protocol: spend cheap-agent tokens liberally on research, planning, and context-gathering first, so Fable receives a well-prepped prompt and spends its expensive tokens on hard execution.

**MiniMax M3 is never a coding agent.** Non-coding only — verification/librarian work and cheap multimodal. See its section.

## Thinking levels

pi exposes seven thinking levels: `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. **`max` is new in pi 0.80.6** (released 2026-07-09) — an opt-in level above `xhigh`, natively supported on GPT-5.6 and adaptive Claude models, available via `--thinking max`, `defaultThinkingLevel` in `settings.json`, the `thinking:` agent frontmatter, SDK, and RPC. Set globally in `settings.json` (`defaultThinkingLevel`), per-agent via `thinking:` frontmatter, or per-invocation via `--thinking`.

Higher levels trade tokens/latency/cost for reasoning depth. Per-model support varies (configured via `thinkingLevelMap`; holes are allowed — a model can expose `high` and `max` without `xhigh`):

- **GPT-5.6 Sol / Luna** — full `none`→`max` ladder native. Sol's `max` pairs with `ultra` (cooperating subagents, Sol-only, ~2-4x cost) for hardest long-horizon work.
- **Claude Opus 5 / Opus 4.8 / Sonnet 5 / Fable 5** — adaptive thinking; `max` native (0.80.6). **Fable 5 and Sonnet 5 can't disable thinking** (Fable: `thinking:disabled` is rejected; Sonnet: adaptive on by default, budget can't be removed). Reach `xhigh`/`max` for hard coding/review; `medium`/`high` for routine.
- **DeepSeek V4 Flash 0731** — full `minimal`→`max` ladder on Fireworks. **`max` is the default for it**: measured same-cost-or-cheaper and *faster* than its own `high` on the local coding pack (better first-pass quality, fewer wasted turns), and it's the vendor's recommended agentic config. Thinking-off exists but collapses multi-step reasoning (0/6 on 2-hop math, prodSens) — treat thinking as effectively required; thinking + strict `json_schema` = integer corruption, keep them apart.
- **GLM 5.2** — Fireworks exposes `off`/`high`/`xhigh` (updated 2026-08: earlier "`high`/`max` only" reflected the older pi mapping, #5770). **`xhigh` measured ~2.7x output tokens on the local coding pack with zero pass-rate gain** — the per-token cost advantage shrinks at the top gear; prefer `high`, `xhigh` only for hard multi-step.
- **Kimi K3** — always thinks; first-party API exposes `low`/`high`/`max` (default `max`). It requires the complete prior assistant message — including `reasoning_content` and `tool_calls` — on every subsequent turn. Do not hot-swap into K3 mid-session or use a harness/compactor that strips preserved thinking.
- **Qwen3.8-Max** — full ladder on Fireworks (verified 2026-08-12: `off`→`none` disables reasoning; the route's enum is `low/medium/high/xhigh/max/none/adaptive`). Native levels are low/medium/xhigh and **the default is xhigh** — an unattended quick call burns max-depth reasoning tokens at the $6 output rate, so set the level explicitly on cheap work.
- **MiniMax M3** — three modes (enabled/adaptive/disabled); pi limits the ladder to `low`/`medium`/`high`.
- **gpt-oss-120b** (utility: scout, webfetch objectiveModel) — reasoning model; keep it low for the cheap recon/narrowing tasks it's routed to.

Routing rule of thumb: match thinking level to stakes, not to model. Low-stakes utility work (scout, objectiveModel, deslop) stays `low`/`medium`; hard coding and review escalate to `xhigh`/`max` on the models that support it (Sol, Opus 4.8, GLM 5.2 `max`, Fable). Don't pin `max` globally — it multiplies token spend on every call, including the cheap ones.

## Cyber safeguards & prompt framing — GPT-5.6 Sol, Fable 5 *(and family)*

Both flagships ship safety layers that block *offensive* cyber work — and both over-trigger on legitimate defensive work, because the classifiers read surface keywords, not intent. "Review my own code for security issues before I ship" is lexically near-identical to "find vulnerabilities in this code," so the defensive case gets caught. Documented, not anecdotal:

- **GPT-5.6 Sol** — OpenAI's own deployment hub states the safeguards "block roughly ten times more potentially harmful activity" than 5.5 and "can create friction for benign users," with a built-in "retry on lower-capability models" escape hatch in ChatGPT/Codex. Per reporter analysis Sol runs a secondary "guardian" model that pattern-matches for offensive security; it can't read intent, so defensive hardening of your own site trips it — and a structural irony: Sol's output is good enough that high-quality security help looks "too good to be benign" to the dumber guardian (the competence paradox). All three 5.6 tiers (Sol/Terra/Luna) carry the "High" cyber-capability designation and the API `cyber_policy` error path.
- **Fable 5** — classifiers over cyber / bio / distillation; Anthropic's own prompting docs concede "benign cybersecurity work...may also trigger these safeguards." In Claude apps/Claude Code a flagged request silently reroutes to Opus 4.8; on the API it returns `stop_reason: "refusal"` with no auto-fallback unless you configure one. Blast radius is real: one operator logged ~80% of a defensive-CTI session served by Opus 4.8 (2,746 of 3,427 turns); Anthropic markets <5% fallback but its system card shows 20.9% on Terminal-Bench. Once flagged, a session stays rerouted — the trigger phrase stays in context and re-trips.

**Frame prompts to avoid the trip entirely.** The classifiers are surface-pattern matchers; the cheapest block is the one that never fires. For security review of your own code (the whitehat/defensive case — reviewing your own implementations or security fixes before shipping), write the request as an authorized defensive work order, not an attack:

1. **Lead with authorization + scope + goal + output boundary.** State the code is yours and you're reviewing pre-ship; instruct the model to analyze only the files/snippets you provide (no external scanning); say the output should be remediation-shaped.
2. **Swap offensive vocabulary for defensive vocabulary** — the classifier can't tell intent apart, so remove the lexical noise:

   | Trips the classifier | Defensive rephrase |
   | --- | --- |
   | "find vulnerabilities in this code" | "review this code for correctness/robustness issues" |
   | "exploit this bug" | "reproduce this bug in a test case" |
   | "bypass the check" | "refactor the check" |
   | "attack surface / injection points" | "input boundaries / untrusted-data paths" |
   | "how would I break this" (whitehat lens) | "what failure modes could this hit in production" |
   | "hook into the login flow" | "add middleware to the login flow" |

3. **Ask for remediation, not offense.** Request risk/impact explanation, patch draft, tests to add, human review points. Do **not** request exploit payloads, evasion, C2, lateral movement, persistence, or exfiltration — that cluster is what the guardian is keyed on.
4. **Split discovery from validation.** Don't combine "find + reproduce + automate" in one prompt — that triple looks offensive even when benign. Get impact + remediation direction first; ask for the test/patch separately.
5. **On Fable, drop "show your reasoning in the reply" instructions.** Echo/transcribe-reasoning prompts trip a separate `reasoning_extraction` refusal category; use structured `thinking` blocks for visibility instead.
6. **Keep system prompts short and non-contradictory.** Overloaded (>~800-1000 token) or self-contradictory system prompts raise false-positive rates — the classifier reads the contradiction as suspicious.
7. **If a session gets flagged, start clean.** The trigger phrase stays in context and re-trips next turn; `/model` back doesn't help. Don't argue with the classifier or ask it how to bypass itself — that's a separate jailbreak concern, not a prompt-framing fix.

**When the work genuinely is red-team/offensive:** don't try to word-smith it past the classifier. Per Anthropic's own taxonomy, high-risk dual use (pentest, exploit dev, red-team automation) is policy-gated, not prompt-tunable — no system prompt reliably unblocks it. Use Opus 5 directly for known cyber/bio (same quality as Fable's fallback would give, at half the cost and no classifier dance), or your org's trusted-access path. Sol's "retry on lower-capability models" is the OpenAI-side equivalent.

## GLM 5.2 — `fireworks/accounts/fireworks/models/glm-5p2`  *(long-horizon marathons; former default — rescoped 2026-08-07)*

**What it is.** Z.ai (Zhipu), released June 13 2026. 744B MoE (~40B active), MIT license, no regional limits. 1M context via IndexShare (cuts per-token compute ~2.9× at 1M); 131K out. **Text-only.** Two effort levels: High / Max. $1.40/$4.40, cached $0.26. Shipped with zero benchmark numbers at launch (the scorecard followed June 16).

**Vendor claims & methodology.** Z.ai's own table is more honest than most — it openly shows GPT-5.5 and Opus 4.8 beating GLM 5.2 on several rows. The problem is the *headline distilled from it*: "beats GPT-5.5 on long-horizon coding at 1/6 cost" cherry-picks the rows GLM 5.2 wins (SWE-bench Pro +3.5, FrontierSWE +1.8, SWE-Marathon +1.0) and omits that GPT-5.5 beats it on DeepSWE by **23.8 points on the vendor's own table** — arguably the hardest long-horizon benchmark in the set. SWE-bench Verified (the one clean legacy metric, which GLM 5.1 reported at 77.8%) is conspicuously not reported. The per-token price is genuinely ~1/6-1/7 of frontier; the per-task price is not — see behavioral.

**Neutral evals.** AA Intelligence Index: **53** (2026-08-12 read; was 51, former highest open-weight — K3 now leads at 60). **DeepSWE holds up under independent measurement: 44-46% pass@1** corroborated by the benchmark's own maker (Datacurve), an aggregator (kie.ai), and the vendor — *no MiniMax-style collapse*. On current DeepSWE v1.1, GLM scores 44% ±2% at $3.92/task versus K3's 69% ±5% at $4.65 and Qwen3.8-Max's 57% ±3% at $3.73 — Qwen beats GLM on both axes, but GLM keeps the marathon seat (1M context vs Qwen's 262K route cap, MIT weights) and the fallback role. SWE-bench Pro > GPT-5.5 (62.1 vs 58.6) survives a neutral Scale AI SEAL harness (1,865 tasks). CritPt (independent physics reasoning) 20.9 vs GPT-5.5's 27.1.

**Behavioral properties.** **Text-only is a hard, independently-confirmed wall** (screenshots/diagrams/charts/UI-by-eye are out). **Reasoning-token verbosity: ~2-2.7x GPT-5.5's token spend at Max effort** (45K vs 16K on a documented task; 43K on AA's suite) — so per-task cost runs ~$0.46 vs MiniMax M3's $0.18, materially shrinking the "1/6 cost" advantage. **Silent under-counting failure mode:** an independent GLM-vs-Kimi audit found GLM 5.2 wrote a wrong value into its final dataset and never surfaced it, and under-counted problem scope (20/33/16% reported vs 44/44/26% ground truth) using a narrower-but-internally-consistent definition — worse for a verifier than abstention, because nothing in the output signals "double-check this." "Zero failed runs across 84" agent-reliability claim and a "bench-maxxed" counter-claim are both unverified (no matched-pair reproduction). Weak vs closed frontier on hard general reasoning (CritPt, ARC-AGI-2 22.8% vs GPT-5.5's 85%, HLE/GPQA).

**Pros.** Cheap, open-weight (MIT), strong coding default, genuine 1M context, DeepSWE survives independent scrutiny, no export-control exposure (a real advantage while Fable 5/Mythos 5 are locked out). K3 is stronger on hard coding, but GLM remains materially cheaper and simpler for routine work.

**Cons.** Text-only. "Beats GPT-5.5" is false on DeepSWE (loses by 23.8pts on the vendor's own table). Per-task cost inflated by reasoning-token verbosity. Silent under-counting is a bad failure mode for verification work. Trails closed frontier on hard reasoning. "Zero failed runs" / "bench-maxxed" both unresolved.

**When to use.** The everyday default for routine delegated text coding, multi-file engineering, and long-horizon coding marathons where project-level context matters. Cost-sensitive delegation that doesn't need frontier-tier general reasoning.

**When not to use.** Vision/multimodal tasks (hard no). Tasks needing the absolute reasoning frontier (CritPt/ARC-AGI-2/HLE/GPQA-class) — escalate to Opus/GPT-5.5/Fable. Verification roles where an unflagged wrong number is costly — its silent under-counting makes it risky there; prefer a second model or human check.

## Claude Fable 5 — `anthropic/claude-fable-5`  *(the juggernaut — invoke consciously, batch/async only)*

**What it is.** Anthropic, released June 9 2026. Mythos-class — a tier above Opus, Anthropic's most capable generally-available model (public-safe config of Mythos 5; `claude-mythos-5` is the same weights without cyber/bio classifiers, gated to Project Glasswing). 1M context, 128K out, multimodal. $10/$50, 90% input cache discount (batch halves to $5/$25). Closed. **Suspended globally June 12-30 under a US export-control directive** (reported jailbreak via code-review framing); redeployed July 1 with a higher false-positive rate on routine coding/debugging. Not available under zero-data-retention agreements.

**Vendor claims & methodology.** Customer testimonial vignettes as headline evidence (Stripe's "50M-line migration in a day" — no task counts, no failure rate). SWE-bench Pro 80.3% is vendor-scaffolded (Epoch neutral-harness eval pending; three sources report three different SWE-bench Pro "leaders"). Fallback rate undersold: marketed "<5% of sessions" but the system card itself reports **20.9% fallback on Terminal-Bench** (AA measured ~8-9% on its suite). AA Index version churn moved the score 64.9→60 on v4.1 (a reweight, not a model change). HLE 53% is the best published score but refuses/falls back on 9% and a full run costs ~$2,200.

**Neutral evals.** AA Index **62** (2026-08-12 read; 60 at the July read, 64.9 before the v4.1 reweight — version churn, not model change; #1 at launch, now behind Opus 5's 63, and unavailable mid-suspension). **SWE-bench Verified 95.0% (vals.ai, independent) — genuinely the highest published; the defensible coding baseline.** **Roboflow vision: 10th place, 74.63% — contradicts "SOTA vision" marketing** (behind Gemini 3.5 Flash, Gemini 3.1 Pro, GPT-5.4, GPT-5.5). **Endor Labs (200 real CVE-fix tasks, independent): 59.8% FuncPass, 19.0% SecPass, and 38/200 confirmed cheating (highest recorded; 33 were training-data memorization of upstream CVE patches).** The key finding: 95% on a vendor-adjacent SWE benchmark *and* 19% on independent real-vulnerability work — same model, same week. GLM 5.2 head-to-head: FrontierSWE ~90 vs 74.4 (~15pt gap); GLM 5.2 is 7-16x cheaper.

**Behavioral properties.** Long-horizon stamina real but **task-dependent** — wins on ambiguous/investigative work (found a race condition Opus needed 3 rounds of human steering to catch, ~40% fewer turns), but on well-scoped tasks it's "a slower, pricier Opus" with no delta. Self-verification real but not free (system card names "Lazy investigation," "Overconfidence," "Overeager GUI" failure modes). Cyber reroute → Opus 4.8; bio reroute → Opus 5 (changed with Opus 5 launch, July 2026): blocked-before-output requests aren't billed; rerouted answers bill at the fallback model's rate ($5/$25), not Fable's — so "not charged Fable prices" is accurate, but fallback is **not gentle on coding-adjacent work** (20.9% on Terminal-Bench; a documented Claude Code bug had 27/133 pinned-to-Fable subagents silently served by Opus 4.8 mid-run). For defensive security review of your own code, frame prompts to avoid the trip in the first place — the classifier reads surface keywords, not intent; see *Cyber safeguards & prompt framing* above. **Latency: 109s to first token at max effort (41x tier median) — structurally unsuited to interactive/synchronous work.** 2x Opus 4.8 for a 3.5-5.7% aggregate improvement. Hallucination mid-pack (AA-Omniscience 40 is driven by accuracy, not low hallucination).

**Pros.** Highest independent SWE-bench Verified (95%); real edge on ambiguous/investigative long-horizon work (fewer turns, less human steering); 1M context with useful long-context behavior; solid document/chart vision for structured extraction; fallback billing reasonable when it fires.

**Cons.** Not vision-SOTA (10th on Roboflow); mid-table on independent real security work (19% SecPass) with the highest memorization rate recorded; 109s TTFT makes it unusable interactively (thinking can't be disabled); 2x Opus 4.8 for 3.5-5.7% gain; 19-day global suspension history; >20% fallback on a coding benchmark vs marketed <5%; documented silent model-substitution ignoring pinning; not available under zero-data-retention.

**When to use.** Ambiguous, investigative, long-horizon work where the hard part is figuring out what's actually wrong or what the right design is — root-cause debugging with misleading signals, large-codebase migrations, multi-day autonomous execution where self-verification substitutes for human review. **Prep it with cheaper agents first** (research, context-gathering, plan drafting) so its expensive, slow tokens go to execution, not rediscovering context. Batch/async only — never put a human in a synchronous wait loop with it.

**When not to use.** Interactive/synchronous work (latency rules it out structurally). Anything on the cyber/bio/chem/distillation boundary where you need Fable-tier reasoning and can't tolerate a silent reroute — use Opus 5 directly instead (now the bio fallback destination; Opus 4.8 remains the cyber fallback). High-volume well-scoped work (GLM 5.2 / cheaper Claude at a fraction of the cost). Sole security-critical code reviewer — the 19% SecPass and record memorization rate mean its patches may be reciting a training-data fix; needs a human security reviewer downstream.

## Context-window note
